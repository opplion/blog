## 引入

传统可观测方案（如链路追踪）通常要求开发者在业务代码里手动接入可观测系统的 SDK，这带来两个问题：一是观测系统与业务系统强绑定，SDK 升级要跟随业务一起发版；二是埋点逻辑侵入业务代码，侵入性高、不利于长期维护。eBPF 提供了一条新路径——不修改业务代码，直接从内核侧获取观测数据，让观测能力与业务解耦。

## eBPF 快速入门

eBPF 程序是一种运行在内核里的受限程序：它有 11 个 64 位寄存器、固定指令集，且不能随意调用内核函数，只能通过内核提供的 helper 函数访问数据（读写 map、读取事件上下文、获取时间戳等）。程序通常由 C 语言编写，通过 LLVM 编译成 eBPF 字节码。

### 执行链路

1. 用 C 或 Rust 编写 eBPF 程序，经 LLVM/Clang 编译成 eBPF 字节码。eBPF 采用 RISC 风格的 BPF 指令集（注意：是 BPF 自己的 ISA，不是 RISC-V）；
2. 用户态通过 `bpf()` 系统调用把字节码交给内核；
3. 内核把程序交给 BPF 验证器，验证器逐路径检查程序的安全性；
4. 验证通过后由 JIT 编译器翻译成当前架构的原生机器码并加载到挂载点执行；没有 JIT 的架构退回解释器。

## eBPF 实现原理

Linux 通过"受限环境 + 静态验证 + 即时编译"三层机制保证 eBPF 程序安全，而不是靠一个传统意义上的虚拟机：验证通过后程序以原生机器码直接跑在 CPU 上，不存在解释执行层的"隔离"，完整的机制主要是由下面三个模块组成的。

### eBPF 验证器

eBPF 程序运行在内核空间，一个错误程序足以让整个内核崩溃，所以内核在加载时对程序的正确性要求极高。验证器承担的就是这个职责：

- 限制循环为有界循环，保证程序必然终止；
- 检查所有内存访问都在栈、map 或事件上下文的边界内，禁止任意的指针算术；
- 逐条指令、逐路径地模拟程序状态空间，证明任何输入下都不会产生非法行为。

验证器是 eBPF 安全的基石：程序能否运行，靠的不是"相信开发者"，而是被机器证明安全。

### JIT 编译器

验证通过的字节码交由 JIT 编译器翻译成目标架构（x86_64、arm64 等）的原生机器码，执行性能接近手写内核代码。相比解释执行，JIT 消除了逐指令的解释开销，这是 eBPF 能用于高频路径（例如每个网络包都要处理）的前提。JIT 并非强制：没有 JIT 的架构退回内核解释器，但多数生产特性要求 JIT 可用。

### 数据通道：map

eBPF 程序本身是无状态的——每次事件触发都是一次全新执行，因此跨事件的状态、以及和用户态的通信，全部通过 **map** 完成。内核程序用 helper 函数读写 map，用户态用 `bpf()` 系统调用读写同一个 map。按用途可以分为几类：

- **跨事件传参**：kprobe 入口钩子把参数写进 map，出口钩子取出来——同一次系统调用的两个钩子之间传递数据；
- **长期状态**：连接表、会话表这类需要跨事件累积的数据；
- **配置下发**：用户态把过滤规则、符号偏移表写进 map，内核程序读取；
- **事件外送**：perf event array / ring buffer 型 map，把内核事件流式交给用户态处理。

## 观测落点

eBPF 能观测到什么，取决于程序挂在哪类挂载点上：

- **kprobe / uprobe / tracepoint**：分别观测内核函数、用户态函数和内核静态事件。其中 uprobe 通过内存页副本上的断点实现，不修改被观测程序的二进制文件——用户程序无需重编译、无需重启即可被观测；
- **XDP / tc**：网络数据路径上的高性能观测；
- **perf event**：CPU、内存等采样类观测。


**Q: eBPF 程序怎么拿到事件信息？**
> 📌 `ctx` —— 触发现场的入口参数。** eBPF 程序的入口签名统一是 `int prog(struct pt_regs *ctx)`，但 `ctx` 里装什么随挂载点而异，通常会有内核函数的寄存器现场，借此获取内核事件。

## 实战：一个 TCP 调用收集器

理论讲完挂一个具体例子。我在实验仓库里放了一个完整的可运行示例——[tcp-call-collector](https://github.com/opplion/playground/tree/main/tcp-call-collector)，用 eBPF 收集 TCP 协议栈上的调用事件：内核侧一个 C 文件、用户态一个 Go 文件，适合对照本文拆解。

### 挂点与事件

示例在 TCP 协议栈的 5 个函数上挂了探针，对应 4 类事件：

| 事件 | 挂载点 | 说明 |
|------|--------|------|
| CONNECT | `kprobe/tcp_v4_connect`、`kprobe/tcp_v6_connect` | 客户端发起建连 |
| ACCEPT | `kretprobe/inet_csk_accept` | 服务端接受连接 |
| SEND | `kprobe/tcp_sendmsg` | 发送 |
| RECV | `kprobe/tcp_recvmsg` | 接收 |

跑起来后另开一个终端 curl 一下，就能看到类似输出：

```
CONNECT  curl    88912  10.1.2.3:53412 -> 142.250.72.14:443
SEND     curl    88912  10.1.2.3:53412 -> 142.250.72.14:443
RECV     curl    88912  10.1.2.3:53412 -> 142.250.72.14:443
ACCEPT   server  2087   127.0.0.1:8080  <- 127.0.0.1:53472
```

### 和上文对上号的几个细节

- **kprobe 的参数**：`tcp_v4_connect` 的 `BPF_KPROBE` 宏按参数声明直接展开成对寄存器（`PT_REGS_PARM1/2/3`，x86_64 上是 rdi/rsi/rdx）的读取——这就是"事件上下文"：内核函数调用的现场。
- **kretprobe 拿返回值**：`inet_csk_accept` 返回的子 socket 只在返回点存在，入口钩子拿不到，必须挂 `kretprobe` 读返回值寄存器。
- **CO-RE 读内核结构体**：五元组（地址/端口）从 `struct sock` 上读取，字段访问都带 `__builtin_preserve_access_index`，加载时由内核 BTF 按字段名重定位偏移。`bpf/common.h` 里的 `sock_common` 只声明用到的几个字段，布局不必与内核一致。
- **`bpf_probe_read_user` 读用户内存**：建连的目的地址在入口时还没写到 socket 上，要从用户态 `sockaddr` 参数读。
- **ringbuf 外送**：事件写入 `BPF_MAP_TYPE_RINGBUF` 型 map（`events`），用户态用 ringbuf reader 读出来打印——对应上文 map 分类里的"事件外送"。
